# Scope Change Audit: TripNest AI reduced to two core features

Date: 2 November 2026. Supersedes the feature scope in `PROJECT_AUDIT.md` (kept as history).

**Product scope from now on:** (1) tourist crowd prediction, (2) smart destination recommendation. Everything else is future scope and is not presented as implemented.

## Safety measures taken before any change

- A full backup of the project (without `.venv`) was written to `hackathon 2.0/tripnest-ai-backup-before-scope-change.tar.gz`.
- **Nothing is deleted.** Modules outside the two core features are *unplugged* (no longer mounted in the API or linked in the UI) and kept on disk under `legacy/` folders or as unmounted files, so they can be restored. No database tables or rows are dropped.

## Reuse or unplug, module by module

| Module | Where | Decision | Why |
|---|---|---|---|
| Destination and attraction catalogue, 36 states/UTs | `models.py`, `data/catalog.py`, `routers/catalog.py` | **Reuse** | Destination data, kept separate from observations and predictions |
| Demonstration crowd history generator | `services/crowd_sim.py` | **Reuse** | Source of the labelled demonstration observations |
| Forecasting model, chronological train/validation/test, two baselines | `services/forecast.py`, `scripts/train_model.py` | **Reuse** | Core feature 1 |
| Crowd levels, uncertainty band, best times, batching and cache | `services/crowd.py`, `services/runtime.py` | **Reuse** | Core feature 1 |
| Place photos with credit | `services/photos.py` | **Reuse** | Recommendation cards need images |
| Crowd heat map data | `/api/crowd/map` | **Reuse** | Visual crowd indicator |
| Destination comparison | `/api/crowd/compare` | **Reuse** | Required comparison step |
| Recommender | `services/recommender.py` | **Rewrite in place** | New inputs (start location, date, one interest) and a transparent four-factor score that consumes predictions; popularity is no longer a factor |
| Location handling | none existed | **New** | City gazetteer search, manual entry, optional browser location |
| Destination prediction endpoint | none existed | **New** | Date and time-range prediction, uncertainty, best time, week trend |
| Accounts, profiles, favourites | `routers/auth.py` | **Unplug** | Registration is no longer needed for discovery or prediction |
| Itinerary planner | `routers/planning.py`, `services/planner.py` | **Unplug** | Removed module |
| Community posts and comments | `routers/community.py` | **Unplug** | Removed module |
| Reviews and sentiment | review routes in `routers/catalog.py`, `services/sentiment.py` | **Unplug** | Removed module |
| Weather dashboard | weather route, `services/weather.py` | **Unplug** | Removed module |
| Traveller crowd reports | report route | **Unplug** | Needed accounts; no live source is claimed |
| Admin console | `routers/admin.py` | **Unplug** | Large admin dashboards removed |
| Local listings | listing seed rows | **Unplug** | Marketplace removed |
| Single-page web app (landing, Discover, explore, planner, community, admin) | `frontend/assets/js/*` | **Replace; old files moved to `frontend/legacy/`** | Replaced by three simple pages |

## Dependencies checked before unplugging

- `routers/catalog.py` mixed core and removed endpoints. The removed ones (reviews, weather, reports) move to `routers/legacy_extras.py`, which is not mounted.
- `recommender.recommend()` lived inside `routers/planning.py`. The new recommendation route lives in a new `routers/discover.py`.
- Seed data still creates demo reviews and listings in the database. Left in place (no data is destroyed); nothing reads them.
- `bcrypt`, `PyJWT` and `email-validator` stay in `requirements.txt` only because unplugged code imports them. They can be removed when the legacy code is deleted with approval.

## Proposed simplified architecture

```
Browser: 3 pages (Home, Results, Destination), vanilla JS, Leaflet map
   │  JSON over HTTP
FastAPI
   ├─ /api/locations      city search + manual resolve (static gazetteer, no external service)
   ├─ /api/recommendations  four-factor score using predictions
   ├─ /api/destinations/{slug}/prediction  date + time-range prediction
   ├─ /api/crowd/compare, /api/crowd/map, /api/destinations, /api/*/photo
   └─ /api/model, /api/health
Services: forecast (ML), crowd (levels), runtime (cache, batching), recommender, photos
Data: SQLite (dev) / PostgreSQL (prod): catalogue tables; observations are generated by crowd_sim; model artefact in backend/models
```

## Risks

- Crowd numbers remain demonstration data. Every screen says so.
- Photos depend on Wikimedia being reachable; cards fall back to a plain tile.
- Distance is straight-line (haversine), labelled as such.
